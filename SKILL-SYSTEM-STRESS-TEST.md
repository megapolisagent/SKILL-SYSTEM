# Skill System — стресс-тест на реальных Skills

Проверка модели из `SKILL-SYSTEM.md` (`DRAFT → EVALUATED → VERIFIED → VERIFIED·LIVE → NEEDS REVIEW → DEPRECATED`) на реальных артефактах владельца. Источники: `AI_OS` и `Chief Design Officer`. Foundation не использован.

## Что реально найдено

**Chief Design Officer — ноль кандидатов.** Это не Skill-библиотека. Единственный Skill-подобный элемент там — `docs/lenses/` (Product Psychology, Visual Systems, Interaction, Typography, Narrative, Brand Character), и сам проект прямо это отрицает: `Chief Design Officer.md` строка 61 — «**Lenses** — `docs/lenses/`. **Not skills — nothing here is executed.**» Честно фиксирую: подходящего материала для стресс-теста здесь нет, ничего не притягиваю искусственно.

**AI_OS — семь артефактов в `skills/`**, из них выбраны три, максимально разных по форме и сложности:

1. **`skills/youtube-analysis.md`** — простой Skill. Детерминированная процедура (субтитры → транскрипция → кадры → сообщить об ограничении), без frontmatter вообще, явно вызывает другой Skill по завершении.
2. **`skills/idea-calibration.md`** — сложный workflow Skill. Обязательный 8-шаговый gate перед архитектурными решениями, свой формат лога, falsification-шаг, retrospective.
3. **`skills/conversion-method/SKILL.md`** — единственный артефакт в формате папка+`SKILL.md`+YAML-frontmatter (`name`, `description`) во всём `AI_OS`. Явно самоописан как experimental-гипотеза с собственным критерием подтверждения/опровержения.

Артефакта со `scripts/`/`references/`/`assets/` в `AI_OS` не найдено — `conversion-method/` содержит только `SKILL.md`, больше ничего. Честно фиксирую отсутствие этого типа, не имитирую его.

Ещё три файла (`taste-capture.md`, `capability-creation-methodology.md`, `opportunity-discovery.md`) не взяты как основные образцы, но использованы как подтверждающие: `taste-capture.md` использует третий, ещё один вариант метаданных (`Skill: / Тип: / Версия: / Дата:` — не YAML, не пусто); `opportunity-discovery.md` и `capability-creation-methodology.md` дают дополнительные данные к находкам ниже.

## Skill 1 — `youtube-analysis.md` (простой)

**FACT**: нет frontmatter, нет заявленного статуса. Тело — жёсткая последовательность (субтитры → транскрипция → кадры → сообщить об ограничении), с конкретной технической деталью, явно взятой из реального сбоя («Авто-субтитры... дублируют строки построчно... обязательно дедуплицировать, иначе файл в разы длиннее»; «кириллица ломается через кодировку bash/PowerShell при прямом выводе»). Последняя строка: «После завершения анализа — автоматически переходить к Opportunity Discovery (`skills/opportunity-discovery.md`)» — прямой, безусловный вызов другого Skill.

1. **Однозначное состояние?** Нет. Текст читается как проверенный в реальной работе (конкретные найденные баги), но в артефакте нет ни одной явной evidence-записи об этом — только косвенный, нечитаемый системой сигнал.
2. **Evaluation evidence?** Здесь оценка — это не «лучше ли текст со Skill», а «была ли соблюдена последовательность исчерпания способов, не пропущен ли шаг». Ближе к проверке соответствия процедуре, чем к сравнению качества результата.
3. **Usage evidence?** Прямое соответствие модели — просто счётчик реальных вызовов, без сложностей.
4. **Где неоднозначность?** (а) стартовое состояние неизвестно системе, хотя фактически Skill явно не «черновик»; (б) у модели нет места для факта «этот Skill безусловно вызывает другой» — если `opportunity-discovery.md` изменится или устареет, эффект на `youtube-analysis.md` никак не отражён.
5. **Что реально нужно?** Способ честно завести уже существующий, непроверенный нашей системой артефакт — не как `DRAFT` (это неверно описывает его реальную зрелость) и не как `VERIFIED` (у нас нет для этого evidence).
6. **Что лишнее?** Ничего в модели не оказалось лишним для этого случая.
7. **Чего не хватает?** Формального различения evaluation-как-проверки-соответствия от evaluation-как-сравнения-качества (см. синтез ниже) и явного места для факта «вызывает другой Skill» (уже отмечено как открытый вопрос в `SKILL-SYSTEM.md`, здесь — первое реальное подтверждение, что вопрос не гипотетический).

## Skill 2 — `idea-calibration.md` (сложный workflow)

**FACT**: нет frontmatter. Обязательный gate («Все 8 шагов обязательны, если gate вызван») с собственным форматом лога, шагом Falsification и разделом «Light Retrospective» — три вопроса, которые Skill сам задаёт себе после каждого запуска, если хотя бы одна из осей Impact/Uncertainty/Complexity была high. Текст содержит встроенные, датированные заметки о прошлых сбоях и внесённых из-за них правках («наблюдалось в сессии 2026-07-27: без явного триггера здесь агент несколько раз садился проектировать экран... — Контракт глубины для Large-масштаба... обязательная последовательность этапов, не факультативная»).

1. **Однозначное состояние?** Ещё труднее, чем в кейсе 1. Внутри самого файла уже видна история ревизий по итогам реальных сбоев — по сути, Review уже происходил, неоднократно, но как проза внутри тела файла, не как отдельная запись evidence.
2. **Evaluation evidence?** Сравнение «с Skill / без Skill» плохо определено: это не генеративная задача с сопоставимым выводом, а протокол принятия решения, последствия которого (хорошая или плохая архитектура) видны месяцы спустя, а не сразу.
3. **Usage evidence?** Технически считается так же, как везде. Но: gate явно и намеренно срабатывает редко («меняется способ решения задачи» — это не рутинная ситуация). Низкая частота вызовов здесь — признак того, что gate работает правильно, не признак того, что Skill не нужен.
4. **Где неоднозначность?** (а) Evaluation-через-сравнение плохо подходит для решений с длинным горизонтом последствий; (б) staleness-триггер Review («не использовался за период») почти гарантированно даст ложный сигнал именно на этом Skill; (в) у Skill уже есть собственный, встроенный, срабатывающий на каждый запуск механизм самопроверки (Light Retrospective) — и не очевидно, как он соотносится с системным Review, у которого другой триггер (не «после каждого запуска», а «по staleness/изменению/запросу»).
5. **Что реально нужно?** Ничего нового не добавляю только из-за этого случая — но он прямо подтверждает то, что `SKILL-SYSTEM.md` §7 уже пометил как нерешённое (usage=0 → Review не должно быть жёстким правилом). Это не новая проблема, а первое реальное доказательство уже зафиксированного риска.
6. **Что лишнее?** Ничего.
7. **Чего не хватает?** Явного разделения «встроенная в сам Skill самопроверка» (Self Check/Retrospective — работает при каждом исполнении, автор — сам Skill) и «системный Review» (работает по внешнему триггеру, решает человек) — сейчас в модели это не различено по имени, и есть риск однажды их перепутать.

## Skill 3 — `conversion-method/SKILL.md` (эталонный формат)

**FACT**: единственный найденный артефакт в целевом формате — YAML `name`+`description`, markdown-тело. Явно маркирован: «Статус: experimental (рабочая гипотеза), не подтверждённая универсальная методология». В конце файла — собственный, чётко сформулированный критерий: подтверждение — «при создании второго агента... ядро не потребовало изменения логики рассуждения»; опровержение — «второму агенту пришлось переписать сам метод». Есть собственный шаг «Self Check» внутри тела (шаг проверки, который выполняет сам Skill во время работы, не про статус артефакта).

1. **Однозначное состояние?** Лучший из трёх случаев — есть явный самообъявленный статус и чёткий критерий. Но статус не выведен нашей системой, а вписан автором в прозу.
2. **Evaluation evidence?** Здесь ломается граница, заложенная в `SKILL-SYSTEM.md` §6. Наша модель предполагает, что Evaluation — это то, что мы сознательно организуем (тест-кейсы, прогон, сравнение). Критерий этого Skill — противоположный: подтверждение приходит только тогда (и если), когда реально появится второй агент, который начнёт использовать этот метод. Это не спланированная проверка, а накопленное со временем наблюдение — по механике ближе к тому, как мы описали Usage, чем к тому, как мы описали Evaluation.
3. **Usage evidence?** Прямое соответствие модели, без сложностей.
4. **Где неоднозначность?** Ровно в п.2 — сам факт квалификации доказательства (спланированный тест vs. накопленное наблюдение реального будущего использования) не описан в модели никак.
5. **Что реально нужно?** Это не единичный случай — тот же самый принцип, дословно, использован во втором независимом файле: `capability-creation-methodology.md` («Критерий подтверждения — в конце файла, тот же принцип, что у `conversion-method/SKILL.md`»). Один и тот же паттерн подтверждён дважды, независимо, с явной самоссылкой автора на то, что это осознанно повторяемый приём — это ровно тот случай, когда, по вашему правилу, изменение оправдано, а не «неудобный случай один раз».
6. **Что лишнее?** Ничего.
7. **Чего не хватает?** Второго режима Evaluation-evidence — не только «прогнали тест-кейсы и сравнили», но и «зафиксировали заранее заданный критерий, который подтвердится или опровергнется реальным будущим использованием». См. изменение ниже.

## Синтез

### Где модель работает без проблем
- Artifact/Registry/Validation — ни один из трёх случаев не создал вопросов к этим трём зонам.
- Usage evidence (счётчик + свежесть + дата последнего вызова) — работает одинаково чисто на всех трёх, включая Skill с намеренно редким вызовом (кейс 2).
- Разделение «usage ≠ доказательство качества» — не просто не сломалось, а прямо подтвердилось кейсом 2: gate с низкой частотой вызовов был бы неверно помечен как «сомнительный» по частоте, если бы usage подменял собой качество.
- Разделение DEPRECATED-не-удаляется, human approval на переходах — не проверялось напрямую (ни один образец не в этом состоянии), формальных противоречий не возникло.

### Где модель ломается
1. **Стартовое состояние для уже существующих артефактов не определено.** Все три образца (и, судя по остальным четырём просмотренным файлам, скорее всего вся папка `skills/`) написаны до появления этой модели. У системы нет честного способа завести их — не как `DRAFT` (недооценка), не как `VERIFIED` (нет evidence).
2. **Evaluation в модели предполагает только один режим — спланированное сравнение.** Реально встречен второй, независимо подтверждённый дважды режим: заранее объявленный критерий, подтверждаемый или опровергаемый естественным будущим использованием, а не постановочным прогоном. Для workflow-Skill с длинным горизонтом последствий (кейс 2) само понятие «сравнение с/без» тоже плохо определено — это третий, ещё не решённый вариант той же проблемы.
3. **Встроенная в Skill самопроверка (Self Check, Light Retrospective) и системный Review — разные механизмы с разными триггерами**, но модель их никак не именует раздельно. Встречено в двух из трёх образцов.

### Что действительно необходимо изменить (внесено в `SKILL-SYSTEM.md`)
Только то, что подтвердилось независимо минимум дважды или системно во всех образцах — не единичные неудобства:
- **Evidence-запись Evaluation теперь может быть одного из режимов**: `tested` (спланированный прогон/сравнение) или `observed` (заранее объявленный критерий, подтверждённый реальным будущим использованием) — подтверждено дважды независимо (`conversion-method`, `capability-creation-methodology`).
- **Провенанс evidence-записи может быть `measured` или `inferred`** — `inferred` для уже существующих артефактов, заведённых в систему без прогона через неё: состояние присвоено по имеющимся косвенным признакам, честно помечено как неизмеренное, а не как проверенное. Подтверждено системно — 100% протестированных образцов.

### Что НЕ изменено, хотя и встретилось
- Расхождение триггера Review (staleness) с намеренно редко вызываемыми Skills — не превращено в новое правило. `SKILL-SYSTEM.md` §7 уже держит это открытым; кейс 2 — первое реальное подтверждение риска, не повод фиксировать конкретный порог сейчас.
- Явный вызов одного Skill другим (кейс 1) — не превращено в поле формата или отдельный механизм composition. Уже открытый вопрос в §9, здесь получил первое реальное подтверждение, не решение.
- Разделение «встроенная самопроверка Skill» vs. «системный Review» — зафиксировано здесь как наблюдение, не внесено в `SKILL-SYSTEM.md`: не мешает ни одному из пяти зон работать, это вопрос терминологической точности на будущее, не архитектурная поломка.

### Открытые вопросы, которые остаются открытыми
- Каким конкретно должен быть порог/период для Usage freshness — как и раньше, не решено, теперь с реальным контрпримером (кейс 2).
- Нужен ли отдельный механизм composition, или её достаточно решать вручную, как сейчас, — реальный пример есть (кейс 1), решения не принято.
- Как по факту квалифицировать `inferred`-evidence при заведении существующего Skill в систему — только что появившийся вопрос из этого стресс-теста, критериев присвоения пока нет.
