# Future Product — следующий этап, не текущая реализация

> Этот документ фиксирует продуктовую цель на будущее. Ничего из описанного здесь не реализовано — см. `skills/capability-recommend/SKILL.md` и `CATALOG.md` за тем, что реально работает сейчас (текстовый протокол поверх существующего Skill System, без UI/API/сервиса).

## Продуктовая цель

Skill System должна получить универсальный пользовательский интерфейс со следующими свойствами:

- человек вводит рабочую задачу обычным языком;
- система показывает подходящие Skills / MCP / Plugins / Agents / Tools;
- показывает отдельно: что уже доступно локально, чего не хватает (GAP), что найдено извне;
- человек может использовать результат напрямую, без посредников;
- Engineer и другие агенты могут использовать тот же механизм программно, не отдельную реализацию под себя;
- при обнаруженном GAP, если вопрос шире точечной проверки факта, к нему может подключаться Researcher как отдельная research-подзадача (не встроенная в Skill System research-механика);
- локальные проверенные ресурсы и внешние непроверенные находки визуально разделены — не смешиваются в одном списке.

## Независимость от Engineer, но общий механизм

Интерфейс — самостоятельная точка входа в Skill System, не часть Engineer и не подчинён ему. При этом сам механизм рекомендации (протокол Find → Match → Gap → Discover → Assemble, `CATALOG.md` как источник данных, делегирование Researcher при полноценном исследовании) — один и тот же для всех: человек пользуется им через будущий интерфейс, Engineer и другие агенты — тем же протоколом программно или через `capability-recommend`. Два разных способа войти в один и тот же механизм, не два разных механизма.

## Что сейчас сознательно не реализуется

- UI (веб/десктоп/что-либо визуальное) — не начато.
- API (HTTP/RPC поверх `skillctl.py`) — не начато.
- Отдельный сервис/бэкенд, отдельный от текущего CLI-инструмента — не начато.

Эти три пункта — следующий этап, наступает только после того, как текущий текстовый протокол (`capability-recommend`) доказал себя на реальных задачах. Не строится заранее «на всякий случай».

## Открытый вопрос на будущее

Как именно человек попадает в интерфейс (веб-страница, расширение, CLI поверх `skillctl.py`, что-то ещё) — не решено и не должно решаться сейчас. Решение принимается после того, как понятно, где реально возникает трение при использовании текущего текстового протокола.
