# idea-calibration
## Обязательный gate перед любым архитектурным решением

Критерий вызова: **меняется способ решения задачи, или только реализация в рамках
уже выбранного способа?** Меняется способ → gate обязателен. Меняется только
реализация → gate не нужен, работаем сразу по Reasoning Pipeline (`CLAUDE.md`).

Если граница неочевидна — решает не интуиция, а три оси Шага 0 (Impact/
Uncertainty/Complexity): хотя бы одна high → считать, что способ меняется.

Типичные случаи, где способ почти всегда меняется:
- предложение нового агента или проекта
- крупное архитектурное изменение (затрагивает >2 модулей)
- масштабирование существующей системы
- любой запрос «нам нужно создать X»
- проектирование интерфейса/навигации/UX для системы целиком, не точечная
  правка внутри уже выбранного экрана (наблюдалось в сессии 2026-07-27:
  без явного триггера здесь агент несколько раз садился проектировать
  экран AI_OS до внешнего research, полагаясь на рассуждение из принципов)

Типичный случай, где способ не меняется: добавить вопрос/поле в уже работающий
механизм, точечная правка внутри уже выбранной архитектуры, исправление бага.

Все 8 шагов обязательны, если gate вызван. Незавершённый протокол — красный флаг,
не повод продолжить.

**Быстрый путь** (для low-risk решений с ясным контекстом):
Шаг 0 → Шаг 1 (Problem Definition) → Шаг 4 (Trade-offs) → Шаг 5 (Routing).
Не отменяет протокол — сокращает его для очевидных случаев.

---

## Шаг 0: Capability Selection Trigger

Три оси. Проверяются всегда, даже на быстром пути.

- **Impact** — решение меняет систему, правила или сущности, на которые ссылаются другие файлы?
- **Uncertainty** — есть недостаток данных, нужен research, неизвестный внешний мир?
- **Complexity** — конфликт принципов, множественные компромиссы, multi-perspective рассуждение?

**Все оси low** → одна строка в логе: «CS Trigger: все low». Переходи к Шагу 1.

**Хотя бы одна ось high** → активировать соответствующее меню:
- Impact high → найти зависимых (кто ссылается на этот файл/правило), флаг если затронуты другие системы
- Uncertainty high → World Research (Шаг 2) не откладывается
- Complexity high → рассмотреть Architecture Review capability, декомпозицию через sub-agents

---

## Шаг 1: Problem Definition

Написать что сломано в одном параграфе.

Обязательно:
- Текущее состояние
- Желаемое состояние
- Кто испытывает проблему (Мария / агент / workflow)
- По возможности — quantify

Если не можешь чётко сформулировать — стоп. Не переходи дальше.

---

## Шаг 2: World Research

Выйти в мир и посмотреть как это решают другие.
Research пропорционален масштабу решения:

| Масштаб | Время | Источники |
|---|---|---|
| Small (minor tweak) | ~15 мин | 1–2 |
| Medium (new tool/config) | ~45 мин | 3–5 |
| Large (new agent/architecture) | ~2 часа | 5+ |

Ответить:
- Что существует на рынке?
- Как другие архитектуры это решают?
- Какие trade-offs они выбрали?

Приоритет источников: официальная документация > инженерные статьи первоисточника
> реальные реализации (код, конфиги, открытые репозитории, публичные примеры
использования) > реальный пользовательский опыт из первых рук (форумы, Reddit,
сообщества — конкретные истории использования, не общие мнения) > вторичные
обзорные статьи и блоги — в таком порядке, не любой источник равноценен.
Пользовательский опыт из первых рук — не то же самое, что вторичный блог-обзор:
первое обычно вскрывает реальные ограничения при масштабировании, второе — часто
пересказ документации. Для задач проектирования интерфейса/навигации/UX третий и
четвёртый уровни обязательны, не факультативны — одной официальной документации
недостаточно (см. типичный случай в Шаге 0).

Документировать: timestamp + источники + confidence level (High/Medium/Low).

**Контракт глубины для Large-масштаба** (обязательная последовательность
этапов, не факультативная — наблюдение 2026-07-27: без явного минимума
research останавливается на поверхностном web-поиске, даже когда триггер
уже сработал):
1. Первичный обзор — актуальным доступным поисковым инструментом (проверить
   `routing/registry.md` → WorldResearch, executor может отличаться от
   записанного там «предпочтительного», если тот фактически не подключён —
   не гадать, не притворяться, что недоступный инструмент использован).
2. Открытые репозитории/реализации — обязательны, если для темы существуют
   open source проекты (GitHub и т.п.), не факультативны при наличии.
3. Реальный пользовательский опыт из первых рук — обязателен, если решение
   касается инструмента/практики, которой реально пользуются люди (форумы,
   Reddit, сообщества) — конкретные истории, не общие мнения. Если прямой
   доступ к источнику технически недоступен — использовать вторичные
   источники, явно цитирующие/пересказывающие первичный опыт, и пометить
   это ограничение достоверности в отчёте, не выдавать за прямой доступ.
4. Официальная документация — обязательна для проверки заявленных
   возможностей, но не единственный источник и не последняя инстанция сама
   по себе.
5. Синтез — не менее 5 реальных продуктов/паттернов, сравнение по единой
   матрице с одинаковыми критериями для всех вариантов; организовать вокруг
   паттернов/подходов, не только вокруг названий продуктов — продукт
   иллюстрирует паттерн, не самоцель.
6. Гейт вывода — финальная рекомендация запрещена, пока этапы 1–5 не
   пройдены. Решения, конфликтующие с уже принятыми ограничениями системы
   (например SSOT), исследуются на этапах 1–5 полностью честно — с явной
   пользой и явной ценой, не исключаются из обзора заранее; само
   ограничение применяется только здесь, на Шаге 5 Routing этого протокола,
   не подавляет сбор информации раньше.

## Шаг 3: Generate 3 Alternatives

Придумать ТРИ разных подхода. Не один, не два. ТРИ.

Для каждого: описание 2–3 строки + что нужно + time to working loop.

- **Вариант A (Minimal)** — самый простой path
- **Вариант B (Scale)** — более амбициозный path
- **Вариант C (Hybrid)** — альтернативный path

Если не можешь придумать три — возвращайся к research.

---

## Шаг 4: Trade-offs Analysis

Таблица 3×3 (вариант × плюсы / минусы / риски).

Дополнительно определить:
- Какой самый простой?
- Какой самый безопасный?
- Какой fastest to working loop?
- Какой сложнее всего поддерживать?

---

## Шаг 5: Routing Decision

Выбрать маршрут и обосновать:

1. **Текущая система** — небольшое изменение в ядре
2. **Существующий проект** — задача в границах проекта, reuse контекста
3. **Существующий агент** — задача подходит без создания новой сущности
4. **Расширение агента** — новая capability внутри существующего агента
5. **Новый агент** — все предыдущие маршруты не подходят; проверить
   Capability Map — пустой узел, связанный со стратегической целью, либо
   независимо повторившийся паттерн запроса (см. CLAUDE.md → Роль AO → Build)

Для выбранного маршрута документировать:
- Какие критерии выполнены
- Почему предпочтительный путь
- Какие риски остаются
- Почему другие маршруты отвергнуты

**Routing Falsification (обязательно):**
- Почему это НЕ нужно как новый агент?
- Какие предположения под риском?
- Что говорит против нового агента?
- Перед custom build: можно ли проверить core assumption более лёгким путём?

---

## Problem Fidelity (обязательно перед Шагом 6)

Сравнить формулировку Шага 1 (Problem Definition) с выбранным маршрутом
Шага 5 (Routing Decision) — решают ли они всё ещё одну и ту же задачу, или
в процессе Research/Alternatives произошла подмена уровня, роли, цели или
объекта решения (определение — CLAUDE.md → Independent Validation). При
обнаружении дрейфа — вернуться к Шагу 1, не продолжать к Decision Point.

---

## Шаг 6: Decision Point

- **Yes** → документировать reasoning, перейти к Шагу 7
- **No** → стоп, валидный outcome
- **Experiment** → определить 2-week scope с exit criteria

Confidence: Low / Medium / High
Если confidence = Low → вернуться к Шагу 2.

Архитектурный анализ завершается одним из двух исходов:
- **Recommendation** (вывод + рекомендация + confidence + обоснование)
- **No Recommendation Yet** (причина + что нужно получить)

No Recommendation Yet — корректный результат.

---

## Шаг 7: Handover

**Если No или Experiment:** залогировать результат, стоп.

**Если Yes:**
- Документировать reasoning в PROJECT_DNA.md проекта
- Выполнить Bootstrap Sequence
- Зарегистрировать в projects/registry.md с пометкой «Created after Idea Calibration»


## Light Retrospective (если хотя бы одна ось была high)

Три вопроса после завершения:
1. CS Trigger был явно проверен и залогирован на Шаге 0?
2. Оценка осей соответствовала фактическому профилю задачи?
3. Сможет ли будущий читатель через 6 месяцев понять решение без реконструкции из предположений?
