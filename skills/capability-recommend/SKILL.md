# capability-recommend

## Что это

Задача → рекомендация, какие уже имеющиеся Skills подходят, чего не хватает, и какие внешние ресурсы можно подключить. Не отдельный движок и не второй агент — рассуждение самого Claude поверх `CATALOG.md`, по фиксированному протоколу.

## Кто пользуется

Универсальный механизм, не инструмент только для Engineer. Одинаково применим, когда задачу формулирует человек напрямую в этом репозитории, Engineer при сборке/доработке агента, или любой другой агент, у которого есть доступ к `CATALOG.md` этого репозитория. Протокол ниже не меняется в зависимости от того, кто спрашивает.

## Главное правило

**Инструмент рекомендуется только потому, что помогает решить именно эту задачу, не потому что существует.** Skill с похожим названием, но не подходящий по смыслу описания (`description`/`when`/`not_when`) — явно называется неподходящим, не притягивается для видимости результата.

## Протокол: Find → Match → Gap → Discover → Assemble

### 1. Find
Прочитать `CATALOG.md` целиком (производный индекс — `SKILL.md` каждого Skill остаётся источником истины, не он).

### 2. Match
Для каждого потенциально релевантного Skill — сверить задачу с его `description`/`when`/`not_when`, не только с именем. Если не подходит — сказать прямо, не подгонять. Если подходит — учесть его `status`: `VERIFIED`/`VERIFIED · LIVE` рекомендуется без оговорок; `DRAFT`/`EVALUATED` — с явной пометкой уровня проверенности.

Если всё нужное покрыто локально — **STOP**, к Discover не переходить. Внешний поиск не запускается «на всякий случай».

### 3. Gap
Явно перечислить, какая часть задачи не покрыта ни одним локальным Skill. Не выдумывать частичное соответствие, чтобы не показывать пустой раздел.

### 4. Discover — только по названному Gap, источник выбирается по типу недостающей возможности, не фиксированным перебором всех источников подряд

| Тип недостающей возможности | Куда идти в первую очередь |
|---|---|
| Нужен MCP-сервер | MCP Registry API (`registry.modelcontextprotocol.io/v0/servers?search=...`) → Anthropic Connectors Directory → Smithery (`smithery.ai/servers`) |
| Нужен Skill | `anthropics/skills` (GitHub) → релевантный GitHub-поиск/awesome-list |
| Нужен готовый bundle (Plugin) | `claude-plugins-official`/`claude-plugins-community` → GitHub |

Не проверять все три ряда, если тип gap понятен — только релевантный.

**Узкая проверка факта vs полноценное исследование — разный путь, не один и тот же.** Проверить конкретный, точечный факт (например, «есть ли в MCP Registry сервер под X») — прямое действие внутри этого же протокола (WebSearch/WebFetch/запрос к API источника из таблицы выше). Но если вопрос шире одного факта — нужно сравнить несколько вариантов, разобраться в незнакомой области, оценить качество/актуальность источника — это не проверка факта, а исследование. В этом случае Discover **не пытается провести исследование сам**, а передаёт его отдельной подзадачей Researcher: узкий бриф + критерий достаточности, зафиксированный до запроса (тот же формат, что уже используется для канала Engineer↔Researcher, `COMMUNICATION.md`). `capability-recommend` не становится вторым Researcher — он делегирует, когда объём вопроса выходит за рамки точечной проверки.

### 5. Assemble
Собрать итог в формате ниже. Порядок применения — логический порядок работы над задачей, не порядок нахождения.

## Формат ответа

```
РЕКОМЕНДАЦИЯ

Задача: <одна строка>

УЖЕ ЕСТЬ В СИСТЕМЕ
✓ <skill> — <status> [оговорка, если DRAFT/EVALUATED]

НЕ ПОДХОДИТ, ХОТЯ ПОХОЖЕ ПО НАЗВАНИЮ  (пропустить раздел, если пусто)
✗ <skill> — <почему не подходит, из description/not_when>

НУЖНО ПОДКЛЮЧИТЬ / НЕ ЗАКРЫТО
→ <часть задачи без локального покрытия>

НАЙДЕНО ВНЕШНЕ (не проверено нашей системой)
⚠ <ресурс> — <источник> — <зачем>

Порядок применения: <шаг 1 → шаг 2 → ...>
```

## Внешнее — никогда не добавляется в библиотеку автоматически

```
FOUND → показано пользователю → решение пользователя →
CANDIDATE → skillctl.py set-origin → skillctl.py evaluate → VERIFIED (по факту, не сразу)
```

`capability-recommend` не вызывает `set-origin`/`evaluate` сам ни при каких обстоятельствах — это всегда следующий, отдельный, осознанный шаг человека, не часть этой рекомендации. Особенно важно при пакетной обработке большого объёма материала (не превращать «нашла 17 Skills» в «добавила 17 Skills» без разбора).
