# legacy-repository-audit
## Проверка старого/внешнего репозитория перед тем, как строить новое

> Собрано 2026-08-13 по итогам трёх реальных прогонов в этой же сессии (`MAIN_ENGINEER`, `AI_OS`, и разбор собственных ошибок при их проверке). Каждый прогон находил настоящую ошибку предыдущего — этот Skill существует, чтобы четвёртый раз так не повторился.

## Главный принцип

**Исследование источника ≠ выбор того, что забрать.** Это два разных, разнесённых во времени действия, не одно. Найдено на практике 2026-08-13 дважды подряд: (1) Engineer заявила, что несколько Skills «не инженерные, остаются владельцу» — не проверив, что они уже стоят в общей библиотеке; (2) пять названных ценными находок выпали из итогового списка без объяснения. Обе ошибки — следствие одного и того же: Engineer незаметно для себя самой превратила «я исследовала» в «я решила», не пройдя через владельца.

Правильный цикл, без исключений: **исследовала → полный инвентарный список (в файле) → для каждой строки проверила, нет ли уже у нас → классифицировала → показала владельцу целиком → владелец решил → только теперь внедрила.**

## Когда нанимают

Владелец называет конкретный старый/внешний репозиторий агента и просит проверить его — обычно перед тем, как строить новых агентов, чтобы не переизобретать то, что уже сделано или уже решено не делать.

## Когда нельзя использовать

- Разбор текущего, живого репозитория самого Engineer/Researcher — для этого есть `architecture-review`/`repository-design`, не этот Skill.
- Ревью кода перед доставкой — не про это.
- Задача не про целый репозиторий, а про один конкретный файл/вопрос — избыточно, читай файл напрямую.

## Входные данные

- Ссылка на репозиторий (обычно GitHub).
- Что уже известно о его происхождении, если что-то известно (не выдумывать, если неизвестно).

## Метод

### Шаг 1 — Клонировать, не трогая оригинал
Скачать read-only копию во временную папку (scratchpad). Никогда не писать в оригинал, не коммитить туда. Явно объяснить владельцу, что значит «клонировать» при первом упоминании в разговоре, если ещё не было — не просто назвать действие.

### Шаг 2 — Идентификация, отдельным сообщением, до глубокого чтения
Прочитать только входные/навигационные файлы (README/CLAUDE.md/дашборд/входная точка). Ответить на три вопроса и показать владельцу **до** перехода к шагу 3:
- Что это за агент/система?
- За что она отвечает?
- Как она связана с текущей системой — предшественник, замена, что-то отдельное, всё ещё живая или остановленная? Если неизвестно — спросить владельца прямо, не предполагать.

### Шаг 3 — Глубокое чтение, по категориям, не по файлам подряд
Систематически, не выборочно: архитектура и принципы; Foundation-аналог (если есть); Skills; MCP/tools; модели и роутинг между ними; permissions; workflows/lifecycle; собственная история решений и самопроверок (decisions/changelog/retrospective — если есть, это самый ценный материал: показывает, что реально проверялось на практике, не только что задумано).

### Шаг 4 — Полный инвентарный список, в файл, сразу
Как только Шаг 3 закончен — **записать каждую значимую находку в файл** `workspace/<дата>-legacy-audit-<имя-репозитория>.md`, одной таблицей, до какой-либо классификации:

| Найдено | Что это | Уже есть у нас? | Где должно жить | Забираем? | Почему |
|---|---|---|---|---|---|
| … | Skill / принцип / методика / инструмент / MCP / контент предметной области | да / нет / не проверено | Skill System / Дом / Engineer / владелец сам | да / нет / UNKNOWN | … |

Разговор — не надёжное хранилище такого списка на потом; файл — надёжное. Ничего не остаётся «интересной находкой» без строки в таблице.

### Шаг 5 — «Уже есть у нас?» — реальная проверка, не по памяти, для каждой строки
Обязательный отдельный подшаг, не пропускается ни для одной строки: свериться с настоящим состоянием — `registry.json`/`HOME.md`/файлами, не с тем, что помнится из разговора или кажется логичным по категории (домен findings — маркетинг/дизайн/инженерия — не решает, есть оно у нас или нет, это отдельный факт). Найдено на практике: находка была отклонена как «не инженерная, не наша» без этой проверки — и оказалась уже в библиотеке три дня как.

### Шаг 6 — Классификация: «Забираем?» и «Почему»
Только после Шага 5 заполнять последние две колонки:
- **да** — куда конкретно (Skill System / Дом / Engineer), с причиной.
- **нет** — с явной причиной: уже есть эквивалент, не подтверждено практикой, устарело, принадлежит владельцу (Craft, не Engineering).
- **UNKNOWN** — если пока не хватает данных для решения. Не выбрасывать из таблицы, не подгонять под «да» или «нет» ради завершённости.

### Шаг 7 — Внешние факты — проверять, не принимать на веру
Если находка сама ссылается на внешний источник (документацию, чужое исследование, конкретную технологию) — проверить источник напрямую (`WebFetch`/`WebSearch`) или через Researcher. Не выдавать чужую цитату за подтверждённый факт без проверки — ни в свою пользу, ни против.

### Шаг 8 — Показать таблицу целиком, дождаться решения владельца
Показать полную таблицу из Шага 4-6 — не куратированную выжимку из «самого важного», не пересказ своими словами. Engineer не решает за владельца, какие строки достаточно упомянуть — решение «забираем/нет» по каждой строке принадлежит владельцу, даже если Engineer уже предложила вариант в колонке.

### Шаг 9 — Исполнение только после подтверждения, по файлу
Открыть файл из Шага 4 заново и вычёркивать строки по нему, не по памяти разговора — особенно если между показом таблицы и исполнением прошло много реплик, в том числе не по этой задаче.

## Self Check («И что с того?»)

Если владелец после отчёта спросит «а что ещё не взяли и почему» — есть ли готовый, полный ответ без необходимости заново перечитывать репозиторий? Если нет — Шаг 4 не был доведён до конца.

Если Engineer поймала себя на фразе «я решила не брать X» до того, как владелец увидел X в таблице, — это нарушение главного принципа, не мелочь. Остановиться, вернуть X в таблицу как предложение, не как решённый факт.

## Checklist

- [ ] Клонировано read-only, оригинал не тронут
- [ ] Идентификация показана владельцу отдельно, до глубокого чтения
- [ ] Прочитано по категориям (архитектура/Skills/MCP/модели/permissions/decisions), не выборочно
- [ ] Полная таблица находок записана в файл `workspace/` сразу после чтения, до классификации
- [ ] «Уже есть у нас?» проверено реально (по файлам/регистру) для каждой строки, не по памяти и не по домену находки
- [ ] «Забираем?» — да/нет/UNKNOWN для каждой строки, ни одна не пропущена
- [ ] Внешние ссылки в находках проверены, не принята чужая цитата без проверки
- [ ] Показана полная таблица владельцу, не выжимка и не пересказ
- [ ] Решение «забираем» по каждой строке — слово владельца, не предположение Engineer
- [ ] Исполнение вычёркивается по файлу, не по памяти разговора
