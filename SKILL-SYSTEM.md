# Skill System

Этот документ фиксирует архитектурное решение: что мы решили построить и по каким принципам это работает. Это не README, не техническая реализация и не полная спецификация — если раздел ниже начинает отвечать на вопрос «как реализовать каждый файл и функцию», это ошибка, которую нужно исправить.

## 1. Цель

Создаём самостоятельную Skill System — библиотеку профессиональных Skills и систему, которая поддерживает их жизненный цикл: создание, проверку, установку, использование, обновление, устаревание.

Foundation пока не является частью этой задачи. Skill System должна быть полезной и понятной сама по себе, без привязки к тому, куда именно Skills потом устанавливаются.

## 2. Ядро

Главная идея системы:

> Skill получает и сохраняет рабочий статус на основании evidence, а не просто факта существования.

Evidence-loop:

```text
Evaluation → Human approval → Verified → Usage → Review → Re-evaluation
```

Это единственное, что реально отличает эту систему от простого каталога уже установленных Skills.

## 3. Skill Artifact

Используем существующий межсистемный формат:

`SKILL.md` (папка + YAML frontmatter `name` + `description` + Markdown-тело, опционально `scripts/`, `references/`, `assets/`).

Не изобретаем собственный формат — это открытый стандарт, уже принятый независимо в нескольких экосистемах (см. исследование мировых Skill-систем). Совместимость важнее собственного варианта.

## 4. Основные ответственности системы

Пять зон, у каждой — только ответственность и граница, не более:

- **Artifact** — что такое Skill и как он упакован. Граница: сам файл/папка, ничего о том, где Skill исполняется.
- **Registry** — где находятся наши Skills и как их искать. Граница: индекс нашей собственной библиотеки, не попытка стать установщиком или каталогом для всего мира. Человеку показывается как визуальный каталог (`explorer.html` — один статический файл, поиск/фильтры/карточки, открывается в браузере без сервера) и как текстовый спутник (`LIBRARY.md`, для агентов и grep). Оба генерируются, не редактируются руками. JSON-файлы (`registry.json`, `evidence.json`) остаются внутренним механизмом, не интерфейсом.
- **Lifecycle** — состояния, через которые проходит Skill, от создания до устаревания.
- **Validation** — технически ли корректно оформлен Skill (структура, frontmatter). Не про то, полезен ли он.
- **Evaluation** — реально ли Skill помогает решать задачу, для которой он написан.

## 5. Lifecycle

```text
DRAFT → EVALUATED → VERIFIED → VERIFIED·LIVE → NEEDS REVIEW → VERIFIED·LIVE / DEPRECATED
```

- Evaluation хранится как история событий (каждый прогон — новая запись, не перезапись).
- Usage хранится как evidence свежести, отдельно от evidence качества.
- Status не является произвольной ручной галочкой — он объясняется историей evidence.
- Human approval обязателен в двух точках перехода: EVALUATED → VERIFIED, и решение внутри NEEDS REVIEW (продлить как VERIFIED·LIVE или перевести в DEPRECATED).
- DEPRECATED не удаляется — Skill остаётся видимым, с историей, просто исключается из «что использовать сейчас».

## 6. Evidence

### Evaluation

- тест-кейсы, использованные при проверке;
- результат со Skill / без Skill (или старая версия / новая версия, если это повторная проверка);
- решение человека и дата;
- история повторных проверок — не перезаписывается;
- **режим evidence** — `tested` (спланированный прогон/сравнение) или `observed` (заранее объявленный автором критерий подтверждения/опровержения, который выполняется или не выполняется реальным будущим использованием, не постановочным тестом);
- **провенанс** — `measured` (evidence получено через саму систему) или `inferred` (состояние присвоено при заведении уже существующего Skill в систему, по косвенным признакам, честно помечено как неизмеренное).

### Usage

- количество вызовов;
- дата последнего вызова;
- использовался ли за актуальный период.

Usage не является доказательством качества — это evidence жизненности/актуальности, не evidence того, что Skill хорош. Доказательство качества остаётся только за Evaluation.

### Классификация и происхождение

Не evidence в смысле §5-7 (не про доверие), а идентификация Skill — минимальные поля, не таксономия, придуманная заранее:

- **category** — направление, для которого Skill написан (`CORE`, `RESEARCH`, `WRITING`, `STRATEGY`, `ENGINEERING`, `DESIGN`, ...). Список категорий не фиксирован документом — выводится из реально собранного материала библиотеки, растёт по факту, не по плану.
- **origin** — источник (`own` — написан нами, `adapted` — взят снаружи и скопирован как есть), путь к источнику, и, если Skill был приведён к формату `SKILL.md` при добавлении (например, не имел frontmatter), — что именно изменено. Оригинал при этом не уничтожается: сохраняется рядом как отдельный файл.

---

**Изменено после стресс-теста** (`SKILL-SYSTEM-STRESS-TEST.md`, 2026-08-08): добавлены режим evidence (`tested`/`observed`) и провенанс (`measured`/`inferred`). Причина: минимум два независимых реальных Skill (`conversion-method`, `capability-creation-methodology`) используют один и тот же принцип — критерий, подтверждаемый не постановочным тестом, а естественным будущим использованием; без этого их нельзя было честно продвинуть дальше `EVALUATED`. Отдельно — 100% протестированных существующих Skills не имеют стартового evidence для этой системы; без `inferred` их пришлось бы либо неверно занижать до `DRAFT`, либо неверно завышать до `VERIFIED`. Остальные найденные при стресс-тесте трения (порог Usage freshness, composition, встроенная в Skill самопроверка vs. системный Review) намеренно не превращены в новые механизмы — подробности в `SKILL-SYSTEM-STRESS-TEST.md`.

**Изменено при наполнении библиотеки** (2026-08-10): добавлены `category` и `origin`, добавлен `LIBRARY.md` как человеческий интерфейс поверх Registry. Причина: библиотека перестала быть гипотетической (1 skill) и стала реальной (10 skills, два источника — собственные и внешние) — без category список стал нечитаемым, без origin невозможно было честно ответить «откуда это и наше ли», без человеческого каталога JSON остаётся единственным интерфейсом, что прямо противоречило требованию — Skill System должна быть понятна человеку, не только машине.

**Изменено повторно** (2026-08-10, тот же день): `LIBRARY.md` понижен с «интерфейса» до текстового спутника; основным интерфейсом стал `explorer.html` (один статический файл, поиск/фильтры/карточки/деталь по клику, без сервера) — причина: markdown-каталог не воспринимался как настоящий пользовательский интерфейс, несмотря на генерацию и структуру. Отдельно — наполнение из материала Дмитрия расширено с 3 до 20 skills (11 из `anthropics/skills`, 9 из `obra/superpowers`), плюс все 7 собственных из `AI_OS` — итого 27. `garrytan/gstack` сознательно не тронут: его skills структурно завязаны на собственный рантайм (bash-преамбула, вызовы `gstack-*` бинарников, session/config state) — импорт как есть принёс бы нерабочие ссылки на инфраструктуру, которой у нас нет и которую мы осознанно не строим (§8). Отбор из `anthropics/skills` и `superpowers` — по содержанию и относимости к реальным направлениям библиотеки, не по объёму; что осталось не взятым и почему — зафиксировано в отчёте по итогам этого наполнения, не дублируется здесь.

## 7. Review

Три причины инициировать Review:

- Skill не использовался за установленный период;
- Skill изменился после последней Evaluation;
- человек явно запросил пересмотр.

Правило «нулевое использование за период = обязательный Review» пока не финальная истина — это решение, которое нужно проверять на реальных Skills, не аксиома системы.

## 8. Что сознательно не строим сейчас

- собственный формат Skill;
- собственную базу данных;
- marketplace;
- сложный dependency resolver;
- собственный runtime;
- permissions;
- telemetry;
- AI trust score;
- сложную автоматическую систему composition;
- интеграцию с Foundation.

Если проблема не доказана на реальных Skills — механизма для неё нет.

## 9. Open Questions

- Какой период считать актуальным для Usage freshness?
- Насколько Evaluation должна быть обязательной для разных типов Skills?
- Нужна ли composition как отдельный механизм, или её достаточно решать вручную для конкретного набора Skills?
- Что именно считается достаточным evidence для перехода в VERIFIED?
- Нужно ли разделять «качество Skill» и «актуальность Skill» в самих статусах, а не только во внутренней evidence?

Эти вопросы намеренно не закрыты — для ответа пока не хватает практических данных.

## 10. Как этим пользуется человек

Конечный интерфейс — `explorer.html` в корне репозитория: открыть в браузере (двойной клик, `file://`, сервер не нужен), поиск по имени/описанию, фильтры по category и по статусу (чипы), карточки, клик — детальная панель (полное description, origin, история Evaluation, usage). Не JSON и не CLI. `LIBRARY.md` — тот же каталог текстом, для чтения не человеком (grep, будущий агент).

- **Нашла новый Skill** — говорю (агенту или себе), откуда он взят; он добавляется в `skills/`, проходит `validate`, получает `origin` и `category`, появляется в Explorer. Изначальный статус — `DRAFT`, это честное, а не заниженное состояние.
- **Ищу Skill для задачи** — открываю Explorer, фильтрую по направлению или ищу текстом.
- **Смотрю, что вообще есть** — тот же Explorer целиком, без фильтров.
- **Skill изменился** — система сама это увидит по расхождению хэша с последней Evaluation и пометит `NEEDS REVIEW` — не нужно помнить это вручную.
- **Нужен Skill, которого нет** — пока пишется вручную, как и все остальные (никакой автогенерации, см. §8), и добавляется тем же путём, что и любой новый Skill.

## 11. Как с ней будут работать будущие агенты (design note, не реализация)

Агент пока не создаётся (см. §1) — но формат уже выбран так, чтобы не потребовалось отдельного API для него:

- **найти** — прочитать `registry.json` (машиночитаемый список: имя, category, статус, description);
- **понять, что Skill делает** — прочитать сам `SKILL.md` — обычный текст, который любой агент, работающий со SKILL.md-конвенцией, уже умеет читать;
- **получить/использовать** — скопировать папку Skill туда, где агент её исполняет; формат не требует специального экспортного механизма;
- **получить обновлённую версию** — тот же `registry.json` показывает, изменился ли Skill после последней Evaluation.

Ничего из этого не реализовано как код для агента — только то, что формат и `registry.json` уже это допускают, ничего не блокирует.
